🚀 Production Blueprint for 2-Node Synchronous Read-Scale Availability Groups on RHEL 9.8
  • Project: Clusterless SQL Server 2025 Always On Deployment
  • Target OS: Red Hat Enterprise Linux 9.8 (Plow Kernel)
  • Database Edition: SQL Server 2025 Enterprise Developer Edition

🗺️ Architecture Overview: Read-Scale (Clusterless) Availability Group

This database setup handles high availability directly inside the SQL Server engine by setting CLUSTER_TYPE = NONE. By doing this, we completely remove the need for standard Linux clustering software (like Pacemaker). This cuts down on complex system overhead and significantly reduces backend operational costs.

🛠️ 2. Hostname Allocation & OS Firewall Setup

In this section, we configure the basic operating system identity, network names, and system firewalls to make sure both servers can talk to each other safely.

Step 2.1: Name Your Server Nodes

Run these commands on the respective servers to permanently set their identity names:

# Run this on Server 1
sudo hostnamectl set-hostname rhel-node1

# Run this on Server 2
sudo hostnamectl set-hostname rhel-node2

Step 2.2: Map Local Network Names

Open the network hosts file on both servers using a text editor:

sudo vi /etc/hosts

Add these lines at the bottom of the file so the servers know where to find each other:

192.168.20.11 rhel-node1
192.168.20.12 rhel-node2

Step 2.3: Open Firewall Ports

💡 Note on Clusterless setups: Since this is a clusterless setup, we only open the core SQL engine ports. We deliberately ignore standard cluster daemon ports (like 2224 or 5405) because the SQL Server engine handles all database mirroring natively.

Run these firewall rules on both nodes to allow network traffic through:

# Open port 1433 for regular database connection traffic
sudo firewall-cmd --permanent --add-port=1433/tcp

# Open port 5022 for the Always On replication endpoint data stream
sudo firewall-cmd --permanent --add-port=5022/tcp

# Save and reload the active firewall configuration
sudo firewall-cmd --reload

# Install handy tools to test network pipes later
sudo dnf install -y telnet nc

Step 2.4: Test Your Network Connections

Run these tests to verify that the firewalls are open and that the two servers can talk smoothly:

# 1. Ping Test (Test lines from either node)
ping -c 3 192.168.20.11
ping -c 3 192.168.20.12

# 2. Port Test (Run from Server 2 targeting Server 1)
telnet 192.168.20.11 1433
telnet 192.168.20.11 5022

# 3. Port Test (Run from Server 1 targeting Server 2)
telnet 192.168.20.12 1433
telnet 192.168.20.12 5022

🗄️ 3. Storage Allocation & Disk Preparation

In this step, we create separate folders for database files, transaction logs, and temporary databases. Keeping these files apart helps improve system performance and isolates data read operations from logging activities.

Step 3.1: Create Folders and Secure Access Permissions

Run these commands on both servers to set up directories and lock them down securely:

# Create separate folders for your data, logs, tempdb, and certificate backups
sudo mkdir -p /var/opt/mssql/sql-data
sudo mkdir -p /var/opt/mssql/sql-tlog
sudo mkdir -p /var/opt/mssql/sql-tempdb
sudo mkdir -p /var/opt/mssql/backup/agcerts

# Hand over full folder ownership to the standard mssql system user accounts
sudo chown -R mssql:mssql /var/opt/mssql/sql-data
sudo chown -R mssql:mssql /var/opt/mssql/sql-tlog
sudo chown -R mssql:mssql /var/opt/mssql/sql-tempdb
sudo chown -R mssql:mssql /var/opt/mssql/backup

# Hardening: Restrict directory permissions so only the mssql user can read/write them
sudo chmod -R 700 /var/opt/mssql/sql-data
sudo chmod -R 700 /var/opt/mssql/sql-tlog
sudo chmod -R 700 /var/opt/mssql/sql-tempdb
sudo chmod -R 700 /var/opt/mssql/backup

Step 3.2: Configure SELinux Security Rules

Since RHEL uses strict SELinux rules, you must label these folders correctly so SQL Server isn't blocked by the kernel:

# Register the new paths into the system's database security policies
sudo semanage fcontext -a -t mssql_db_t "/var/opt/mssql/sql-data(/.*)?"
sudo semanage fcontext -a -t mssql_db_t "/var/opt/mssql/sql-tlog(/.*)?"
sudo semanage fcontext -a -t mssql_db_t "/var/opt/mssql/sql-tempdb(/.*)?"
sudo semanage fcontext -a -t mssql_db_t "/var/opt/mssql/backup(/.*)?"

# Apply the security labels immediately across all folders
sudo restorecon -R -v /var/opt/mssql/sql-data
sudo restorecon -R -v /var/opt/mssql/sql-tlog
sudo restorecon -R -v /var/opt/mssql/sql-tempdb
sudo restorecon -R -v /var/opt/mssql/backup

📦 4. SQL Server 2025 Installation

In this section, we register the official Microsoft package distribution channels, install the core SQL Server 2025 engine along with its native SELinux security module, and complete the initial setup prompts.

Step 4.1: Update Operating System Libraries

⚠️ Important Version Requirement: The SQL Server 2025 SELinux security module requires specific system libraries found in RHEL 9.7 or 9.8. Running older RHEL versions (like 9.4) will cause installation errors due to missing package dependencies.

Run these commands on both servers to pull the latest system updates:

# Clear old package cache and run a full system update
sudo dnf clean all
sudo dnf update -y

Confirm that your version matches your design specification by running:

cat /etc/redhat-release

Step 4.2: Verify Storage Space

The installation files will be placed inside the /opt/mssql folder. Make sure your root (/) folder partition has at least 10 GB of free space before proceeding:

df -h /opt

Step 4.3 & 4.4: Register Repositories and Install SQL Server

Add the official Microsoft package distribution channels to your system repository list on both servers:

# Download the repository configuration files
sudo curl -o /etc/yum.repos.d/mssql-server.repo https://microsoft.com
sudo curl -o /etc/yum.repos.d/mssql-release.repo https://microsoft.com

Install the SQL database server engine and its dedicated SELinux package context modules:

sudo dnf install -y mssql-server mssql-server-selinux

Step 4.5: Initialize the Database Instance

Run the configuration setup script to choose your edition and set your administrative password:

sudo /opt/mssql/bin/mssql-conf setup
  • Edition Selection: Choose option 2 (Enterprise Developer edition - free for development environments).
  • Admin Account: Create a strong, complex password for your main system sa (System Administrator) user.

📷 [Visual Asset: Interactive console menu setup wizard prompt]

Step 4.6: Enable SQL Agent Automation and Start Services

Turn on the background automation engine and add the command tools to your terminal profile path:

# Enable the built-in SQL Agent feature
sudo /opt/mssql/bin/mssql-conf set sqlagent.enabled true

# Add command utilities to your terminal settings path profile
echo 'export PATH="$PATH:/opt/mssql-tools18/bin"' >> ~/.bashrc
source ~/.bashrc

# Set the SQL Server service daemon to start automatically when booting
sudo systemctl enable mssql-server
sudo systemctl restart mssql-server

Run a quick command test to verify local server endpoint connectivity:

sqlcmd -S localhost -U sa -C -Q "SELECT @@SERVERNAME;"

🚀 5. Always On Feature Activation, AG Provisioning & DB Sync

In this step, we turn on the high availability settings, build our database security certificates, and open a communication link between the servers.

Step 5.1: Enable the High Availability Module

Run these commands on both servers to activate the Always On engine features and restart the SQL service:

sudo /opt/mssql/bin/mssql-conf set hadr.hadrenabled 1
sudo systemctl restart mssql-server

Verify that the change saved correctly in your server settings file:

cat /var/opt/mssql/mssql.conf

Step 5.2: Create Keys and Connection Endpoints

Connect to the Primary Server (rhel-node1) using a database client and run this script to set up database master keys and the data listener endpoint:

USE master;
GO
CREATE MASTER KEY ENCRYPTION BY PASSWORD = 'YourStrongKeyPassword99!';
GO

-- Create a security certificate for network authentication
CREATE CERTIFICATE AG_Transport_Cert
WITH SUBJECT = 'Availability Group Replica Transport Authentication',
START_DATE = '2026-01-01', EXPIRY_DATE = '2035-01-01';
GO

-- Set up the database mirroring connection endpoint on network port 5022
CREATE ENDPOINT [Hadr_endpoint]
    STATE = STARTED
    AS TCP (LISTENER_PORT = 5022)
    FOR DATABASE_MIRRORING (
        ROLE = ALL,
        AUTHENTICATION = CERTIFICATE AG_Transport_Cert,
        ENCRYPTION = REQUIRED ALGORITHM AES
    );
GO

Step 5.3: Export the Primary Security Certificate

Run this on the Primary Server (rhel-node1) to back up the authentication key so the secondary server can trust it:

BACKUP CERTIFICATE AG_Transport_Cert
TO FILE = '/var/opt/mssql/backup/agcerts/AG_Transport_Cert.cer'
WITH PRIVATE KEY (
    FILE = '/var/opt/mssql/backup/agcerts/AG_Transport_Cert.key',
    ENCRYPTION BY PASSWORD = 'YourStrongKeyPassword99!'
);
GO

Step 5.4: Transfer Certificate Files Across the Network

Copy the certificate keys from rhel-node1 over to rhel-node2 using a network file transfer:

sudo scp /var/opt/mssql/backup/agcerts/AG_Transport_Cert.* root@192.168.20.12:/var/opt/mssql/backup/agcerts/

Switch to the Secondary Server (rhel-node2) console and update the file permissions so the SQL service can read them:

sudo chown -R mssql:mssql /var/opt/mssql/backup/agcerts/
sudo chmod 600 /var/opt/mssql/backup/agcerts/AG_Transport_Cert.*

Step 5.5: Import Security Keys on the Secondary Host

Connect to the Secondary Server (rhel-node2) and run this database script to import the keys and initialize the matching network endpoint:

USE master;
GO

CREATE MASTER KEY ENCRYPTION BY PASSWORD = 'YourStrongKeyPassword99!';
GO

CREATE CERTIFICATE AG_Transport_Cert
FROM FILE = '/var/opt/mssql/backup/agcerts/AG_Transport_Cert.cer'
WITH PRIVATE KEY (
    FILE = '/var/opt/mssql/backup/agcerts/AG_Transport_Cert.key',
    DECRYPTION BY PASSWORD = 'YourStrongKeyPassword99!'
);
GO

CREATE ENDPOINT [Hadr_endpoint]
    STATE = STARTED
    AS TCP (LISTENER_PORT = 5022)
    FOR DATABASE_MIRRORING (
        ROLE = ALL,
        AUTHENTICATION = CERTIFICATE AG_Transport_Cert,
        ENCRYPTION = REQUIRED ALGORITHM AES
    );
GO

Step 5.6: Initialize the Clusterless Availability Group Object

Connect to the Primary Server (rhel-node1) to provision the logical group structure. Note that we set the cluster type to none to remove daemon overhead:

CREATE AVAILABILITY GROUP [ptag]
WITH (CLUSTER_TYPE = NONE) -- Removes high-overhead Linux clustering requirements
FOR REPLICA ON
    N'rhel-node1' WITH (
        ENDPOINT_URL = N'TCP://192.168.20.11:5022',
        AVAILABILITY_MODE = SYNCHRONOUS_COMMIT, -- Guarantees zero data loss
        FAILOVER_MODE = MANUAL,
        SEEDING_MODE = AUTOMATIC,
        SECONDARY_ROLE(ALLOW_CONNECTIONS = ALL)
    ),
    N'rhel-node2' WITH (
        ENDPOINT_URL = N'TCP://192.168.20.12:5022',
        AVAILABILITY_MODE = SYNCHRONOUS_COMMIT,
        FAILOVER_MODE = MANUAL,
        SEEDING_MODE = AUTOMATIC,
        SECONDARY_ROLE(ALLOW_CONNECTIONS = ALL)
    );
GO

Step 5.7: Connect the Secondary Server to the Replication Pipeline

Run this command on the Secondary Server (rhel-node2) to join the active data stream and allow automatic data seeding:

ALTER AVAILABILITY GROUP [ptag] JOIN WITH (CLUSTER_TYPE = NONE);
GO

-- Authorize the group to automatically build replicated database containers locally
ALTER AVAILABILITY GROUP [ptag] GRANT CREATE ANY DATABASE;
GO

Step 5.8: Add the Production Database to the Live Group

On the Primary Server (rhel-node1), build your database instance, set its recovery type, take a baseline backup file, and connect it to the sync loop:

CREATE DATABASE EnterpriseAppDB;
GO
ALTER DATABASE EnterpriseAppDB SET RECOVERY FULL; -- Full transaction tracking model is mandatory
GO

-- Take initial backups to initialize the transactional tracking chain links
BACKUP DATABASE EnterpriseAppDB TO DISK = '/var/opt/mssql/backup/EnterpriseAppDB.bak' WITH COMPRESSION, STATS = 30;
BACKUP LOG EnterpriseAppDB TO DISK = '/var/opt/mssql/backup/EnterpriseAppDB.trn' WITH COMPRESSION, STATS = 30;
GO

-- Link the database container into your live Always On synchronization channel
ALTER AVAILABILITY GROUP [ptag] ADD DATABASE [EnterpriseAppDB];
GO

Run these diagnostic tools from your server console to check error logs and review system events:

# View the last 100 entries inside the native SQL database log file

🔍 7. Post-Deployment Validation Queries

In this final section, we review the T-SQL system queries used to check replication statuses and track background file synchronization directly inside the database engine.

Step 7.1: Verify Availability Group Replication Health States

Run this metadata query in a SQL window to confirm that your databases are fully synchronized across both replica nodes:

SELECT
    ar.replica_server_name,
    adc.database_name,
    drs.synchronization_state_desc,
    drs.synchronization_health_desc,
    drs.is_local
FROM sys.dm_hadr_database_replica_states drs
JOIN sys.availability_replicas ar ON drs.replica_id = ar.replica_id
JOIN sys.availability_databases_cluster adc ON drs.group_database_id = adc.group_database_id;
GO

SELECT
