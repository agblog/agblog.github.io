🔍 Chapter 6: Post-Deployment Health Verification & Disaster Recovery SOP

This chapter provides the tools to monitor your active synchronization states and the recovery runbook steps needed to manage data center failures manually.

📋 Sequence 1 to 100: Run Database Engine Health Diagnostics

Execute these system validation scripts inside your query window to trace data replication status logs.

001. Run this query to check the active synchronization status descriptions across your database replicas:

SELECT ar.replica_server_name, adc.database_name, drs.synchronization_state_desc, drs.synchronization_health_desc
FROM sys.dm_hadr_database_replica_states drs
JOIN sys.availability_replicas ar ON drs.replica_id = ar.replica_id
JOIN sys.availability_databases_cluster adc ON drs.group_database_id = adc.group_database_id;
GO

📷 [Visual Asset Check: Database output results display confirming active synchronized health mapping tables]

002. Truncate line events and monitor automated file copy background operations by checking this system view:

SELECT start_time, completion_time, current_state, failure_state_desc FROM sys.dm_hadr_automatic_seeding;
GO

📋 Sequence 101 to 200: Disaster Recovery Manual Override

Follow these manual steps if a catastrophic data center failure drops your main nodes and you need to bring your off-site disaster recovery node online.

🛑 Failsafe Override Protocol Notice: When both primary nodes crash, the database engine drops into a protected Resolving loop to prevent split-brain issues. Automated cross-subnet failovers are blocked by design. Follow this phase checklist to force data availability manually.

101. Log into the terminal on your surviving off-site server (DR-DB1) and run these tools to clear resource locks and reset lingering failure counters:

# Clear old node test block constraints and resource tracking logs
sudo pcs resource clear sqlcluster-clone --force
sudo pcs resource cleanup sqlcluster-clone

📷 [Visual Asset Check: Terminal console entries log verifying pcs resource locks removal]

102. Open an interactive SQL query window on the off-site server (DR-DB1) and force the Availability Group online, even with data loss risks:

-- Force failover directly inside the database management query terminal
ALTER AVAILABILITY GROUP [ptag] FORCE_FAILOVER_ALLOW_DATA_LOSS;
GO

103. Run this database update to resume regular transaction log tracking and bring your application processing workloads back online:

ALTER DATABASE [EnterpriseAppDB] SET HADR RESUME;
GO

104. Run this final command on your console to confirm that the cluster has stabilized and that DR-DB1 has successfully assumed the primary role:

sudo pcs status
