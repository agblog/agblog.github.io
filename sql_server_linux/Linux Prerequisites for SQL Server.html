📐 Virtual Drive & Space Reclaiming Strategies

When partitioning your virtual storage arrays during the Linux installation setup phase, adhere to these layout rules:

  • Device Type Mapping: Always designate the disk layout formatting structures to utilize a **Standard Partition** type profile.
  • Reclaim Space Allocation: If you are installing across an old disk, run the **Reclaim Space** option inside the wizard to purge historic volumes and guarantee clean storage tracks.
  • The 185 GB Directory Allocation Matrix: Divide a custom 185 GB chunk from your drive array to isolate the core operating system files. Build separate storage volumes for:
    • /boot (Contains your kernel bootstrap initialization images)
    • swap (The host virtual memory system paging space file track)
    • /home (Segregates individual local user account profile directories)
    • / (The Root primary system operations volume directory block)
  • Expansion Space Insulation: This layout keeps the remaining 281 GB of your physical drive space unallocated (showing as pink in the setup summary charts), keeping it safely available for side-by-side Windows setups or dedicated secondary database storage groups.

🖥️ Baseline Engine Hardware Requirements

Your prepared virtual server node must meet or exceed these physical limits to load and sustain the database engine process daemon successfully:

Resource Constraint Minimum Threshold Specification Operational Performance Notes
System Memory (RAM) 2 GB Minimum Required to safely execute base internal system threads and process memory managers.
File System Type XFS or EXT4 Format Engine filesystems must use these formats. Dynamic formatting models like BTRFS are entirely unsupported.
Available Disk Space 6 GB Free Space Ensures room for base product libraries and system files under the primary installation paths.
Processor Speed 2 GHz Clock Speed Maintains steady computational speeds and query transaction execution.
Processor Cores 2 Physical Cores Required to manage basic multi-threaded transaction logs and synchronization loops.
CPU Architecture x64-Compatible Architecture Optimized for 64-bit Intel and AMD processor configurations.

🌐 Supported Operating System Platforms

The core transaction properties are tested, supported, and validated across these system distributions:

  • Red Hat Enterprise Linux (RHEL): Supported on bare metal or virtual containers on versions 7.3, 7.4, 8.x, 9.x, and 10.x.
  • Ubuntu Server: Fully compatible across LTS releases (including versions 16.04, 18.04, 20.04, 22.04, and 24.04).
  • SUSE Linux Enterprise Server (SLES): Supported on version 12 (SP2 to SP5) and version 15 systems.
  • Docker Engine: Supported on version 1.8 or higher platforms on x86-64 processors.

The setup functions are broken into independent packages to maintain a clean filesystem:

  • mssql-server: The foundational database engine container binaries package.
  • mssql-server-agent: Unlocks automation features, execution alerting properties, and background maintenance scheduling.
  • mssql-server-fts: Adds linguistically-aware indexing and text pattern queries via Full-Text Search.
  • mssql-server-ha: Provides high availability clustering integration hooks and Always On data transport loops.
  • mssql-server-is: Enables execution of Integration Services (SSIS) data migration and ETL pipelines.

🔄 Cumulative Updates (CUs) Servicing Guidelines

Microsoft handles product updates through Cumulative Updates (CUs). Observe these operational guidelines during patching tasks:

  • CUs are Collective: Each new CU release completely replaces the older packages and includes all bug fixes, security enhancements, and patches from prior updates. You do not need to apply past updates sequentially.
  • No Need to Install All CUs: You can skip past updates entirely. Only the most recent CU released for SQL Server on Linux is kept available at the main Download Center to streamline your maintenance windows.

🛡️ System User Isolation & Account Security Best Practices

  • Isolate Account Authority: For optimal process safety, database jobs run under a dedicated, limited mssql user. Never start or run instance operations tasks directly under the core operating system root account.
  • Disable the Default 'sa' Account: Immediately after completing the configuration setup prompts and creating an encrypted password tracking string, create a new administrative user, join it to the **sysadmin** role, log in using the new account, and **disable the default sa user** entirely as a baseline security requirement.
